# Screen Color notifications, support prompt and interface tour

## User request

Notify users when a new version is available. After approximately four app openings, ask whether they enjoy Screen Color and offer three buttons: contribute toward Peter's new PC, give feedback, and browse more Cave apps. Make the contribution action colored. Add a guided interface/configuration tour like PlayTime. Investigate the installed app's Windows startup warning. Peter selected the existing Cave support page as the contribution destination.

## Decisions and scope

Keep the existing Electron/CommonJS/plain DOM stack, PlayTime themes and Iconsax library snapshots. No new dependencies, production build, installer upload, push or merge. Implement the already-authorized features locally on dev. A fresh installer is a later explicit action. Do not edit Peter's Cave or PlayTime for these features.

Updates: use the public ScreenColor GitHub Releases API from main only, on app start and every six hours, plus Check for updates in Settings/tray. Read only a bounded small JSON response, with timeout, cancellation and coalesced simultaneous requests. Accept only a newer stable vX.Y.Z release with the exact matching Windows x64 installer filename and canonical repository URL. Ignore drafts, prereleases and malformed/untrusted links. Show an in-app available-update banner plus compact-panel notice, Settings version/status, and a Windows notification at most once per newly detected version. Downloads only start on an explicit Download update click through main-validated release metadata; never auto-download/install or execute an installer. Offline and rate-limit failures remain quiet for automatic checks, explain retry in Settings, and preserve a previously discovered update. Dismiss banner per version, retain update in Settings. No GitHub token or user data is sent. Smoke mode uses injected release responses and never makes update requests.

App experience: persist launch count, tour completion, one-time support prompt dismissal and notified/dismissed update versions in a separate atomically written experience.json with backup. Preserve existing settings.json schema, profiles and enabled intent. Count initial explicit launches and subsequent explicit second-instance launches. Exclude Windows --background launches, renderer reloads and ordinary tray show/hide. The once-only support prompt becomes eligible at count >=4 and is displayed on the next visible full app workspace. Do not open a hidden full app just to show it. Once-only dismissal persists; if saving fails show a retry instead of falsely marking it saved. Queue dialogs behind an active tour/profile dialog. Three primary actions open fixed help/feedback/apps destinations in the system browser, with Contribute to the PC fund visually colored and a separate dismiss/Not now control. Do not claim a payment was made or that donations are currently open.

Tour: a welcome dialog on the first visible full workspace offers Take the tour and Skip for now; neither silently adjusts color values or startup preferences. Explain image comparison, five adjustment controls, starter filters and saving personal profiles, effect/reset, tray controls, Appearance/Windows startup and updates, and how to quit and restore colors. Spotlight actual elements and navigate/scroll to them. Back/Next/Done/Skip, step count, keyboard operation, focus containment and restoration, reduced motion and viewport clamping. Skipping or finishing persists completion; Settings offers Replay interface tour. The initial tray-only startup stays compact until the user opens the full workspace; do not interrupt quiet background launch. No color/appearance actions are triggered by the tour itself.

Startup fix: Electron 33's getLoginItemSettings().openAtLogin reads by AppUserModelID while setLoginItemSettings({name:'Screen Color'}) writes by name. Read the exact user-scoped named Run command and StartupApproved state, including the legacy unquoted command that launchItems may miss. Quote executable and source folder paths for Windows command-line parsing. Configure first installed launch or repair the known legacy command, preserve explicit opt-out and Windows StartupApproved disabling on later launches; never re-enable a user's Windows choice on every launch. Serialize the entire preference transaction (decision, marker, registry and controller commit); restore the original command and approval state on failure. Detect absent keys/values without matching localized error text. Smoke must not touch the real Screen Color startup entry.

## Verification and evidence

Failing then passing meaningful unit tests: strict versions/release URLs and assets; offline/timeout/oversize/error preservation/concurrency; persistence/backup/invalid experience, fourth-launch counting and prompt priority; startup named entries/path quoting/disabled approval and explicit opt-out. Actual isolated Electron smoke checks cover IPC snapshots/actions/invalid destinations and shared popup update state. Browser checks cover welcome/tour all steps, skip/replay/persistence, profile-dialog scheduling, support buttons/color/keyboard/focus, banner dismiss/Settings retry and responsive layouts with fixture metadata. Do not download an installer. Capture matching original before/after settings views in central UI History; current app before captures already available and new matching frames will be taken before UI edits.

## Assumptions made by the implementer

One-time support prompt, rather than recurring every four launches; deliberate process launches count, not tray clicks. Update notification has a manual download action rather than silent download/install. Use green for contribution within existing semantic palette; feedback and more apps remain neutral. First tour waits until full workspace is opened. These choices satisfy the brief without adding startup interruptions.
